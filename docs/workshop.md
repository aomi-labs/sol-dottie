# Sol Dottie workshop

## User story

“Your Solana desk in one conversation. Check a token, explore a venue, and decide what to do next.”

QR opens the deployed landing page. Web users open Dottie and connect a Solana wallet; Telegram users open the configured bot. Research/quotes use the same app and skills on both surfaces. A web handoff requests a fresh quote; it does not imply migrated chat or wallet state.

Builder reveal: “RugCheck, FluxBeam and Solomon are app extensions. Aomi supplies common protocol skills, wallet approvals and transaction execution.”

## Eight-minute demonstration

- 0–1: Open Dottie from QR; introduce the assistant and wallet ownership.
- 1–3: “Check FLUXB, then show a direct FluxBeam quote for 0.01 SOL.” Show evidence and the transfer-fee caveat. Name the venue.
- 3–4: If a custom write has passed release gates, review and approve that trade and show its confirmed receipt. Otherwise explicitly say direct FluxBeam execution is pending; use a separately authorized, rehearsed core Jupiter trade only if available and clearly name it Jupiter.
- 4–5: “Explain USDv rewards and inspect my wallet.” Show Solomon's current enrollment/observation state, not old vault staking. Enrollment remains in the official app until verified.
- 5–6: “Find NVDAx and request a Jupiter quote for 10 USDC.” No purchase is implied by the quote.
- 6–8: Open repo: frontend, provider, app tool, skill and manifest. Show how a custom integration composes with core runtime tools.

## Sixty-minute core workshop

0–10 product demo and runtime boundary; 10–20 import template and configure identity; 20–35 extend a RugCheck read tool and playbook; 35–45 run provider tests and conversation evals; 45–55 activate via Build and exercise verified billing; 55–60 try the app and discuss extensions.
